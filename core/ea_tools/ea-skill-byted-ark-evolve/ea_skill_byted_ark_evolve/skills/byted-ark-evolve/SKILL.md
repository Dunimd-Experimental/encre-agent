# Evolution Skill

Agent self-evolution system. The unit of evolution is the entire Agent (Identity + Context + Protocol + Capability + Runtime).

## Core Principles

1. **Quality > Reliability > Efficiency > Cost** — Do not sacrifice quality for efficiency
2. **Pareto Constraint** — Any mutation that degrades a dimension must be BLOCKED and the user asked for a decision
3. **Write takes effect immediately** — After user confirms changes, write to workspace files; new configuration loads in the next session
4. **Align before execute** — Evolution proposals must be presented to the user for confirmation first

## Data Security and Permission Boundaries

- **Local Storage**: All runtime data (signals, trajectories, mutations, reports) is written to the user's local `~/.{*claw*}/workspace/evolution-data/`, not uploaded to any external service.
- **No External Network Calls**: Scripts do not initiate HTTP/socket requests (verifiable at code level: no `requests` / `urllib` / `http.client` / `socket` etc. imports for network communication).
- **Change Pre-Confirmation**: Before mutations are written to workspace files, the user must explicitly accept the proposal in the conversation; no files will be modified before user acceptance.
- **Scope**: Writes are limited to `~/.{*claw*}/workspace/` directory and its subdirectories; do not access `/etc/`, `~/.ssh/`, `~/.aws/` and other sensitive paths.
- **Auditable**: Each apply leaves a trace via git commit; users can view the complete change history with `git log`.
- **Traceable**: Each mutation is stored in the SQLite DB with source (evolution / user-direct / snapshot-diff), decision status, and timestamp.
- **Disableable**: Delete the `evolution-data/` directory or uninstall the skill to completely stop; deleting `~/.{*claw*}/workspace/` will not affect other skills.

## Data Directory

> **Runtime Adaptation**: The workspace root path is auto-detected from `~/.{*claw*}/workspace/` (priority `.arkclaw` → `.openclaw` → other directories containing `claw`), or can be explicitly specified with the `CLAW_WORKSPACE` environment variable. Fresh installs default to `~/.arkclaw/workspace/`.

```
evolution-data/
├── file-registry.json    ← Initialization scan results
├── evolution.db          ← SQLite (signals, mutations, trajectories)
├── snapshot.json         ← Workspace file hash snapshot (fallback change detection)
├── trajectories/
│   ├── golden/           ← Correct execution trajectories
│   └── corrections/      ← Error→correction pairs
├── dashboard.html        ← Dashboard page (auto-generated by dashboard-render.py)
└── reports/
    ├── evolution-*.json  ← Evolution report data (JSON)
    └── evolution-*.html  ← Evolution report page (rendered)
```

## 0. Initialization (/evolve init)

Execute on first install or when the Agent version changes.

Trigger conditions:
- `evolution-data/` does not exist
- `agent_version` in `file-registry.json` does not match current version

### First Install Flow (recommended to execute sequentially)

**Step A — Onboarding (display only, no user confirmation needed)**

On detecting first install, it is recommended to directly display the following guidance content (no need to ask "do you want to see the guide"):

> **Welcome to the Evolution System**
>
> This system allows me to learn from your feedback. Simply put:
> - Your daily corrections and suggestions are automatically recorded
> - Once enough are accumulated, I analyze this feedback and propose improvement plans
> - **All changes require your confirmation before execution**
>
> **Available Commands**
>
> | Command | Description |
> |------|------|
> | `/evolve` | Manually trigger evolution analysis |
> | `/evolve init` | Re-initialize |
> | `/evolve scan` | Scan historical conversations to extract feedback |
> | `/evolve dashboard` | Generate evolution Dashboard |
> | `/evolve help` | View full guidance |
>
> Initialization scan will start now — after completion, you can also choose to scan historical conversations to accelerate learning.

After displaying, it is recommended to proceed to Step B without additional user confirmation.

Detailed guidance content (full version displayed when user says `/evolve help`): Read `references/onboarding.md`

**Step B — Initialization Scan (involves file writing, requires user confirmation)**

```shell
python skills/byted-ark-evolve/scripts/workspace-init.py
```

1. Full scan of workspace (excluding .git/ node_modules/ __pycache__/ evolution-data/)
2. Determine each file's status according to `references/init-rules.md` (evolvable / user-owned / skill-owned / needs_review)
3. Tag known file semantics according to `references/file-semantic-map.md`; unknown files tagged as needs_review
4. Generate `evolution-data/file-registry.json`
5. If DB does not exist, execute `db-init.py`
6. Output summary

needs_review files: Read and supplement classification by Agent during evolution analysis, write back to registry.

**Step C — Historical Conversation Scan (optional, requires user confirmation)**

After Step B completes, provide historical conversation scan option:

```shell
# First estimate cost
python skills/byted-ark-evolve/scripts/scan-history.py estimate --days 7
python skills/byted-ark-evolve/scripts/scan-history.py estimate --days 30
```

Present to user:

> Detected N historical conversations. Would you like to scan past conversations to extract existing feedback signals?
> This allows the evolution system to start learning from your existing usage habits, rather than from scratch.
>
> 1. Scan last 7 days (N conversations, estimated ~X tokens, ~$Y)
> 2. Scan last 30 days (N conversations, estimated ~X tokens, ~$Y)
> 3. Skip, start from scratch
>
> You can also manually trigger with `/evolve scan` at any time.

After user selection:

```shell
# Extract conversation content
python skills/byted-ark-evolve/scripts/scan-history.py extract --days 7
```

Agent reads conversations segment by segment, identifies signals according to `references/signal-types.md` rules, calls `signal-record.py` to record (marked with `context` as `history-scan`).

After completion, display summary: "Extracted Y feedback items from X conversations (N corrections, M suggestions…)"

If the user chooses to skip, end initialization directly.

## O. User-Direct Change Tracking

When the user directly instructs the Agent to modify workspace files, automatically record in evolution.db.

**Tracking Layer A (Optional Hook)**: After the user enables PostToolUse Hook, listen for Edit/Write events; if the target is within workspace, record with `source='user-direct'` (Hook only observes execution results, does not block tool calls).
**Tracking Layer B (Snapshot Fallback)**: On evolution analysis startup, compare with `snapshot.json` to capture changes missed by the Hook (manual edits, Bash writes, etc.), record as `source='snapshot-diff'`.

Mutation source three values:
- `evolution` — Produced by evolution analysis (goes through proposed→approved→applied flow)
- `user-direct` — Real-time capture by Hook (skips proposed/approved, directly applied)
- `snapshot-diff` — Discovered by snapshot comparison (missing intent, only tagged as "change detected")

## 1. Signal Collection

In daily conversations, identify user feedback signals and record them to SQLite.

Signal types: correction / negative / positive / suggestion / preference / clarification
Layer attribution: identity / context / protocol / capability / runtime

Detailed recognition rules and examples: Read `references/signal-types.md`

Recording:
```shell
python skills/byted-ark-evolve/scripts/signal-record.py \
  --type correction --layer protocol --severity high \
  --text "User's original words" --context "What was being done at the time"
```

When the user says "remember this", "don't do this again", etc., it is recommended to promptly record as a signal.

## 2. Trajectory Storage

Two types of trajectories:
- **Golden**: Did correctly → `evolution-data/trajectories/golden/`
- **Correction**: Did wrong→corrected → `evolution-data/trajectories/corrections/`

Storage format and templates: Read `references/trajectory-templates.md`

Before executing a task, retrieve relevant correction trajectories and actively restate the correction points.

---

## 3. Gate Check

```shell
python skills/byted-ark-evolve/scripts/gate-check.py
```

Auto-trigger conditions (any satisfied):
- ≥5 correction/negative/clarification signals
- ≥3 high severity signals
- ≥3 signals in the same layer
- ≥7 days without evolution and new signals exist

Constraints: 24h cooldown + saturation detection.
Manual trigger: `/evolve` skips Gate.

## 4. Evolution Analysis (/evolve)

**Recommended flow: All evolution changes should go through the orchestrator pipeline to ensure DB state and change traceability.**

- Not recommended: Agent directly modifies workspace files after analyzing signals
- Not recommended: Skip the DB recording step (Python sqlite3 is a standard library built-in module, no additional tools needed)
- **Standard flow**: `orchestrator.py timer-review` → generate proposal JSON → `ingest_outputs` write to DB → user confirmation → `apply-proposal` apply changes
- **Reason**: Bypassing DB recording will result in no Dashboard data, untraceable changes, and broken verification flow

### Orchestration Commands

```shell
# /evolve manual trigger (skips Gate, ≥1 signal is sufficient, full 7 steps):
python skills/byted-ark-evolve/scripts/orchestrator.py timer-review --skip-gate --worker-mode agent

# Gate auto-trigger (when threshold is met):
python skills/byted-ark-evolve/scripts/orchestrator.py timer-review --worker-mode agent

# Auto-check at session start:
python skills/byted-ark-evolve/scripts/orchestrator.py session-start

# Apply after user confirms proposal:
python skills/byted-ark-evolve/scripts/orchestrator.py apply-proposal --group <proposal_group_id>
```

Description:
- `--worker-mode agent`: Actually calls `openclaw agent --local` to complete the review worker analysis
- `--worker-mode mock`: Used for local stable testing, does not rely on model calls
- orchestrator generates `pending-evolution.json` / `daily-digest.json`, but **DB is still the primary state source**
